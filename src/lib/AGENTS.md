# Financial execution rules

- Scalping entry serializes on the tier row, reserves full win payouts across all users by UTC expiry day, and debits stake plus existing account and protocol fees in the contract-insert transaction; accepted terms and payouts never shrink - why: concurrent orders cannot exceed budgets or strand debits after rejection.
- Operations health uses protected aggregates and durable rate-limited provider samples with expiry - why: monitoring never fabricates continuous availability.
- Financial confirmations, corrections and withdrawal holds commit atomically; credited transfer identities are deduplicated and enabled high-value reviews require distinct operators - why: prevent duplicate credits and stranded funds.
- Configuration revisions are immutable and trigger-captured; restoration uses recent operator 2FA, audit reasons and an unchanged-value guard - why: never overwrite a newer configuration.
- Staff authorization uses caller-readable user_roles and fails closed; high-risk operator actions check recent verified app TOTP sessions - why: privileged reads must not establish authorization.
- Prime membership uses cleared wallet collateral and a safe architecture/fee projection; service-only atomic promotion is gated by administrator-enabled policy and server-verified AUM/ETH requirements - why: pending funds and client-selected levels cannot grant financial privileges.
- Membership reads run inside the authenticated component, not a route loader, while the shared layout uses a render-only auth gate - why: server document loads have no browser bearer session.
- Institutional credit simulations persist only user-owned support tickets with Treasury Operations subjects and frozen scenario results; never call financial execution helpers - why: review workflows must not fabricate credit or change balances.
- VIP ecosystem configuration lives in platform_settings with authenticated safe projections and audited administrator writes; customer/staff queries refresh every five seconds - why: one persisted policy synchronizes gifts, portal metrics and promotion without exposing internal notes.- Support history clearing: "both" hard-deletes; one-sided clears set hidden_from_staff_at / hidden_from_customer_at, enforced by a restrictive customer RLS policy and staff loader filters - why: either side can be cleared without losing the other side's record.
